# How the failwise plugin works

The failwise plugin runs a design-side FMEA on software and writes a JSON analysis and an HTML report. This page describes shipped behaviour only: what the plugin does now, not how it came to do it.

## The analysis document

An analysis is one JSON document against `skills/fmea-software/schemas/fmea.schema.json`, whose `$id` is `urn:fmea-software:schema:fmea:v3`. Six parts are authored — `meta`, `elements`, `functions`, `dependencies`, `chains` and, when the run follows flows, `flows` — and a seventh, `computed`, is written only by `validate.ts --write`. No part may carry a property the schema does not declare, and no object may carry one key twice: every script refuses such a document when it reads it. Cross-reference, uniqueness and presence-coupling rules live in the validator, each named where it governs.

`meta` carries identity, scope and the planning record: a stable `id`, the `name`, a `version` that is 1 at creation and is bumped by every update, the `branch` (always `DFMEA`; a process FMEA gets an answer, not a document), the `scope` in prose, the `boundary` with its `included`, `excluded` and `security` fields, the `ground_rules` decided before the analysis, the `assumptions`, the `reviews`, the `scales` pin, an optional `tracker` target, `created` and `updated`, and the analysis-level `history`. Every assumption is its own item with text, an owner and an `open` or `closed` status; an input the run lacks becomes an open assumption owned by `user`, never an invented value. A review entry records its date, reviewers and outcome, and only when someone reports one.

`meta.codebases[]` lists the codebases the run covers or reads, each with a `name`, its repository as `repo` in `owner/repo` form, and a `path` when it is a folder inside a monorepo. An in-scope root carries its `codebase`; so does an in-scope child that lives elsewhere than its parent or whose parent is outside the boundary, and an outside element whose repository the run read. A codebase with no repository in the inputs is an open assumption, not an entry.

`elements[]` is the structure. Each element has a dotted `id` of depth 1 to 4, whose segments carry the hierarchy; `parent` is that id with its last segment removed, or null at depth 1. Every element answers three questions in order: its boundary (`in_scope`, `owned_outside` or `third_party`), its role (`service`, `datastore`, `event_stream`, `interface` or `component`), and whether a required security property depends on it working (`security_relevant`, with a rationale when true). An element outside the boundary must be the provider of at least one edge. Every element carries at least one non-catalog `sources[]` entry, and no chain is rated on an element without one.

`functions[]` says what each element must do: a stable `id`, the owning `element`, the `statement`, the `conditions` under which the function is required, and `for_whom`. A function belongs to exactly one element, and a chain reaches its element only through its function.

`dependencies[]` holds one edge per consumer and provider pair, from the consumer (`from`) to the provider (`to`), with a `strength` of `strong` or `weak` and optional `sla` and `limits` in the source's own words. Silence about either field is an open assumption naming the provider and the field, never a placeholder. An element is never its own provider.

`chains[]` holds one denormalized row per failure chain: the function whose loss it describes, the `failure_mode`, the `effects` at local, next-level and end, at least one `cause`, the `trigger`, the `controls`, the three `ratings`, the computed `priority`, the `actions`, the `catalog_refs`, the `stale` flag and the row's own `history`. A cause may link to another chain whose failure mode it is, and then carries the provider's Occurrence as `cited_o` when the consumer's Occurrence cited it. A control is `prevention`, `detection` or `compensating`, `existing` or `planned`, with an evidence kind and reference.

`flows[]` is optional, and its absence is the only way to say a run authored none. A flow has an `id`, a `name`, a `value_priority` of `High`, `Medium` or `Low`, and optional sources, users, steps and `steps_partial`. A flow carries no rating; a chain that names one reads its Severity over that flow's population, as below.

## Ratings, priority and dependencies

Severity, Occurrence and Detection each run from 1 to 10, where 10 is the worst. The anchors are in `skills/fmea-software/references/scales-software.md`, and `meta.scales.version` records the anchors' version for those ratings. Every rating carries its `value`, a `rationale` against the anchors, an `evidence_kind` (`observed_incident`, `test_result` or `estimate`), an optional evidence reference, and a `review` whose status is `provisional`, `rescored` or `authored`. A `rescored` or `authored` review names the person and the date on which they re-scored it.

Severity reads the worst credible end effect the row's causes and trigger produce without a second independent failure, assessed after the existing evidenced compensating controls have acted. Three facts set it: the effect class, the blast radius, and recoverability. Detection is read off the controls the row carries: a value of 1 needs an evidenced detection control that qualifies. Each factor's categorical breaks sit on the shipped table's band cuts, so two runs may differ inside a band without moving a count.

Every rating the plugin suggests is provisional until a named person re-scores it against the anchors, one rating at a time, never by applying a factor. The plugin names no person the inputs do not name, and a priority resting on a provisional rating is never presented as final.

Priority is computed by `priority.ts` alone, never in prose. The shipped table is `skills/fmea-software/data/priority-fmea-software-v1.json`: the skill's own table, with an `id`, a vocabulary ordered highest first as `H`, `M` and `L`, five bands for each factor at the cuts 1, 2 to 3, 4 to 6, 7 to 8 and 9 to 10, and a cell for every one of the 125 band combinations. Priority never decreases as any factor rises; Severity 9 or 10 is never below `M`; Severity 1 is always `L`; and Severity outranks, as a weak inequality, when the other two factors are swapped. `priority.rpn` stores S times O times D for reference and comparison with legacy sheets, and never ranks.

Strength moves no rating: it selects the provider readings a reviewer checks, and it is the subject of the open assumption recorded when a loss-of-access end effect sits on a provider whose inbound edges are all weak.

`priority.ts`, `validate.ts`, `render.ts` and `track.ts` accept `--table-file` for another table, read from no other location. Once a document records a table id, a run that loads another table is refused with `TABLE_ID_MISMATCH`. Only `priority.ts --write --change-table` changes the record, and only when the person asks for that change or confirms the record is wrong; the change is written into `meta.history`. A shape-valid table that breaks a property above is still used: `priority.ts` prints a `warning priority-table-property:` line naming the cells, `validate.ts` records the same finding as a warning, and neither is a refusal.

## Flows, codebases, assumptions and history

A flow is a use-case grouping of functions that a user-valued journey names. Its `value_priority` label orders flows in the report; it is not a rating, a criticality analysis, a safety analysis or a reliability target. Its `users` object describes the referent population: `population` is a label rather than a number, `share` is a fraction an incident record states and naming what it is measured against, `selecting_condition` is a predicate that selects part of the population, and `review` is a status with the same vocabulary a rating uses. A bare count is not a share. A share raises the radius class and never lowers it.

`chains[].flows` names the flows a chain breaks, in the author's order; the first entry is the flow whose class set the Severity band. Each id resolves to a flow and no flow is named twice. For such a chain, Severity's blast radius is read over the named flow with the highest class, and never below the class the same chain reads with no flow named. A chain's Severity rationale states the chosen flow's share of the system's users and quotes the effect clause.

Two assumptions follow from naming flows. When a chain may name more than one flow, the run records that the named populations are treated as disjoint and their union is not computed. When named flows share a step other than the chain's function, it records an assumption that the coupling is not modelled. Each is owned by `user` and written before the rows it governs. A chain-named flow must carry `users`, a non-catalog source and a `users.review` status; while that review is absent or `provisional`, the chain's Severity counts as provisional and the report's warning names the unconfirmed population. A flow whose recorded steps are a prefix without the chain's function reads as subset for that chain, which is the partial-prefix reading.

Codebases, assumptions and history meet in the update mode. An update diffs the new structure against the stored document by id: an element changed when its kind, boundary or security flag changed, or when an edge into it was added, removed or changed; an edge changed when its strength, SLA or limits changed; a flow id is compared byte for byte, so a rename is a removal and an addition. An element's name, description, sources, rationale or codebase is a label and does not count as a change.

The update marks rows stale with one of five reasons, in this order when more than one rule fires: `element-changed`, `function-changed`, `flow-changed`, `control-removed`, `scales-version`. A `flow-changed` row is one whose named flows changed, whose flow's `users` changed, or whose flow's steps started or ended a partial-prefix reading; the update re-reads its Severity and carries Occurrence and Detection forward unless another rule touches them. `scales-version` marks every rated row when `meta.scales.version` is behind the anchors' declared version, and the pin advances in the same run. A row already flagged keeps its existing reason and `since_version` unless an earlier rule now fires; then the reason is replaced and `since_version` is left as it was, and every factor a firing rule touches is re-read even though only the first reason is recorded.

The update writes its summary into `meta.history`, bumps `meta.version`, appends an entry to each re-rated row's `history`, and names the stored copy it kept. Every `meta.history` entry has a version, a date and a change. Two migrations move older documents to the current model, one for the earlier element kinds and one for the v2 edge list; each runs alone in update mode, records itself, bumps the version and marks no row stale, because it preserves meaning. A document from before either migration is refused with `KIND_LEGACY` or `DEPENDENCY_LEGACY`, and the line names the migration to run.

## The five scripts

The plugin has five scripts under `skills/fmea-software/scripts/`, run by Node 24.2 or later. `validate.ts`, `priority.ts`, `render.ts` and `update-check.ts` have no dependencies; `track.ts` starts `gh` for a GitHub target and `acli` for a Jira target. Nothing else the scripts do reaches the network.

**`validate.ts <file> [--write] [--table-file <path>]`** runs the schema checks, the cross-reference invariants, the priority recomputation and the twenty-one machine lints, and computes the quality score. On a clean run, `--write` replaces the `computed` block with the score, the lints, the validation time and the validator version. On any finding it writes nothing and exits 2.

**`priority.ts <file> --write [--table-file <path>] [--change-table]`** writes each row's `priority` from its `ratings` and its `post_priority` from `post_ratings` where one is present. It also writes the loaded table's id into a document recording none. It refuses a document that records another table unless `--change-table` is given, and refuses `--change-table` when the document records no table or already records the loaded one.

**`render.ts <file> --out <report.html> [--force] [--table-file <path>]`** runs the same checks as `validate.ts` and refuses anything the validator refuses, with the same coded lines. It also refuses a document with no `computed` block (`COMPUTED_MISSING`) or with a score or lint list that a fresh validation no longer produces (`COMPUTED_STALE`), so a report never carries stale checks. `--force` overwrites an existing file; without it, an existing file at the output path is `IO_EXISTS`. After a successful render it prints one line counting the provisional ratings against all ratings.

**`track.ts plan|apply|refresh <file>`** tracks the actions. `plan` writes nothing in the document or the tracker; it prints the target with its visibility, each action's outcome, every finding, and the digest that `apply` takes. `apply` recomputes the plan, refuses a stale digest, creates or adopts one GitHub issue or Jira work item per action, and writes the link into the action as soon as the item exists. `refresh` reads each linked item's state and prints a proposal or finding where that state bears on the action's status; it never changes a status, and its `--write` stores what it saw. A public target, or one whose visibility cannot be established, needs `--public-ok` before anything is created.

**`update-check.ts <stored copy> <draft> [--check]`** writes nothing. It prints the structural diff — dependency, element and flow changes, and chains re-pointed to another set of flows — the stale set with each row's rule and the rows it leaves unmarked, the links into removed chains with the chains they may be re-pointed to, the removed flows each chain still names, the outside elements left with no consumer, and the order to re-rate in. `--check` refuses a draft whose flags, ratings or links disagree with those rules (`UPDATE_MISMATCH`), a draft whose chain names a removed flow, or one whose chain names a flow with no non-catalog source. A stored copy that is not the draft's baseline is `UPDATE_BASELINE`.

Every command shares one failure contract. A failure prints exactly one stderr line, `error <CODE>: <message>`, followed by ` at <pointer>` when the failure is located in a document. Exit 1 is a usage failure, including a Node too old to run the script; exit 2 is a validation or update-check failure; exit 3 is an I/O failure. Every script refuses a document in which one object carries the same key twice, with `IO_READ` naming the key and the object; a JSON reader would keep only the last value, and the next write would remove the first. The four commands that replace the document read it again immediately before writing and refuse with `IO_CHANGED` when the file changed after the command read it or last wrote it, leaving the file as the other program saved it. `--write` on `validate.ts`, `priority.ts` and `track.ts refresh`, and `track.ts apply`, all replace the whole file atomically.

## The report and the workflow modes

`render.ts` writes one self-contained HTML file. It carries no JavaScript and loads no outside resource, so it works offline, and it prints in landscape. Its parts appear in a fixed order: a summary strip and a "Needs attention" block under the title and scope; the ground rules, assumptions and review record; the structure, with a table of top-level elements and a table of dependencies; the flows, with their value priority, users, steps and the chains naming each; an index of failure chains sorted by priority; one section per chain, grouped by top-level element; the actions; the automated checks with their quality score and lint list; and a provenance appendix.

The skill runs one of four request shapes. A new analysis begins from a system description. A seeded analysis starts from postmortems and their action items, running the failure step backward from incidents and carrying each incident-derived chain's `source_incident`. A conversion maps a legacy RPN sheet or FMEA spreadsheet to the schema, keeps the sheet's S, O and D values as `authored`, and records every column and every substituted default in `meta.history`. An update brings a stored analysis to a new architecture, as above. Two migrations support older documents, and the schema-v2 migration follows the first one in the same update when a document predates both.

Every shape runs the same seven steps: Plan, Structure, Function, Failure, Rate, Act and Document. Plan fixes scope, boundary, codebases, inputs, flows, ground rules and assumptions. Structure writes elements, flows and dependency edges; Function writes each element's functions; Failure writes each function's chains with effects, causes, triggers, flows, links and controls. Rate assigns S, O and D with rationales and the review gate. Act records each action's owner, target date and status from the five-value vocabulary. Document writes the JSON, then runs `priority.ts --write`, `validate.ts --write` and `render.ts` in that order, and hands over the report with the provisional-ratings caveat and every open assumption as a question.

## Invariants, lints and the test gates

The validator enforces the schema and named invariants the keyword subset cannot express: id uniqueness and resolution for elements, functions, chains and actions; the parent and id agreement; source presence; codebase and flow resolution; flow step and user coupling; dependency endpoints and pair uniqueness; cause-link resolution, self-links and cycles; review dates; post-rating presence; handoff coupling; stale version bounds; and priority agreement with the loaded table. Each defect is reported once, and the message names the invariant.

The twenty-one machine lints run over the analysis alone. They cover a trigger-less Occurrence estimate, an unevidenced Detection 1, provisional ratings, seeded actions, metadata without ground rules, tracker links, dependency rows, security flags, repository references, cause links, flow coupling, provisional flow users, edge reliability, conversion substitutions and table properties. A lint is a `blocker` or a `warning`; a blocker whose pointer lies inside the chain rows dirties that row, and the quality score is 100 times the fraction of clean rows, rounded, and is 0 when there are no rows or when any blocker points outside them.

Five gates protect the tree. `node tools/run-tests.ts` runs the skill and tool suites under `node --test`. `node tools/check.ts` runs five static checks in order: the TypeScript type check, `oxlint` with type-aware rules and warnings denied, the `fallow` dead-code, duplication and complexity analysis, `tools/check-prose.ts` against the prose baseline, and `tools/check-docs.ts` against the documentation caps. `node tools/check-browser.ts` renders the fixture and checks the report in real browsers at 320, 375, 768, 1280 and 1920 pixels and under print emulation, failing on horizontal scroll, an element past the edge, or an accessibility violation. `node tools/compare.ts` renders the report from the working tree and from a base commit and compares them view by view in the same browsers. The Pages workflow renders `dev/fixtures/checkout-service.fmea.json` into the site it deploys, which is how the published example report exists.

## Provenance, licensing and limits

Every statement in the skill's reference files either cites a verified record id or is tagged `skill-authored`, and an untagged sentence is a defect. The tag vocabulary, the per-source permission rule and the source register are in `skills/fmea-software/references/provenance.md`; a record id resolves through that register. The evidence and process records live in the private `nzneit/failwise-research`. A finding id of the form `F-WSn-NN` is the research report's synthesis and does not resolve publicly, so it is never cited as a source.

The plugin is Apache-2.0, and the attribution its dependencies require is in `skills/fmea-software/licenses/NOTICES.md`. No AIAG-VDA handbook cell value or band boundary ships: the priority table is the skill's own. No Google SRE Book text is reproduced, paraphrased or adapted, and no IEC 60812 text is paraphrased. Nothing specific to a consuming application ships: no service name, team name, incident id or architecture detail from a real system.
