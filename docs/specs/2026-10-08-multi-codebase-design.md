## 1. Purpose

A run over several services and repositories must deliver two outcomes the v2 format cannot.

1. **Trace a failure across services.** A cause on one service's chain is the failure mode of another service's chain, and the document records that as a reference. The dependency between the two services is an edge of its own, with its own strength, so two consumers can depend on one provider differently.
2. **Read the analysis per service or codebase.** The document can say which codebase each element belongs to (§4), the report counts chains per root, and the report's chain rows are grouped by root.

Set aside by the user on 2026-10-08, and listed in §17 as later work: updating one codebase alone after a change in it, and a tracker target per team. The one tracker target per analysis stays as it is.

## 2. What v2 offers and where it stops

Schema v2 (PR #24) added three things for a run over several codebases: `meta.boundary.included` lists each codebase as a prose string; a `repo` source ref may take the qualified form `owner/repo@commit:path`, with the lint `repo-ref-form` checking that once one ref is qualified every ref is; and several systems may sit at depth 1 with no artificial root above them.

What stops there. A codebase is not an entity: nothing ties an element to its repository except a string inside a source ref, so nothing can group, count or check by codebase. A dependency is unary: the block on the provider says how "the analysed system" depends on it, so with two in-scope services the dependency of checkout on pricing has no edge to live on, and strength cannot differ per consumer. Hierarchy is containment and ids are one namespace, so a gateway two services call must nest under one of them or be a root of its own. The next-level effect is prose, so a failure that crosses a service boundary is traced by reading.

## 3. Decisions

| # | Decision | Ruling |
|---|---|---|
| M1 | Scenario | Both at once: several services that form one flow, each in its own repository and often with its own team, and one product spread over several repositories. The codebase is a sourcing concern and a structure concern in the same run. |
| M2 | Unit of grouping | The root, the depth-1 element the hierarchy already provides, plus a codebase record in `meta` that each element may point at by id. The report sections by root and names the codebase of each. |
| M3 | Dependencies | Edges from a consumer element to a provider element in a required top-level part, `dependencies[]`, each with its own strength, SLA and limits. The dependency block on the element is removed. |
| M4 | Trace | A chain-to-chain link on the consumer's cause, `causes[].chain`, naming the provider's chain whose failure mode the cause is. No element reference on the effect: the next-level element of the linked (provider's) chain's effect is the element of the linking (consumer's) chain, found by inverting the links, and where no chain is linked the effect stays prose. |
| M5 | Format | Schema v3, with a pre-schema gate that refuses a v2 document by one issue naming the migration, and a migration performed by the skill's update mode. Not an additive change on v2, which would keep two ways of recording a dependency and keep "the analysed system" in the vocabulary, the very notion a multi-service run makes ambiguous. |
| M6 | Report | The chain index is unchanged. The chain rows are grouped under one heading per root. Two tables are added to the Structure section and a codebases list to the header. |
| M7 | Stale reason | `element-changed` covers a change to an edge into the element and, on a consumer row that §10 marks stale, a change to the edge its link crosses. No new reason, so the closed vocabulary and the ordering rule stand. A `dependency-changed` reason is listed in §17 as the alternative if the stale notice ever needs to be precise. |
| M8 | Strength | Dependency strength moves no rating (§11). The weak-dependency exclusion of the scales is removed and Severity rests on the end effect alone, as the anchors demand. Strength keeps two informational uses: it selects the dependency rows' next-level and end readings, which are a default the run checks against the inputs before rating, and the report prints every edge. The flow-level fact strength stood in for is later work (§17, §20). |
| M9 | Severity lint scope | The machine lint `cause-chain-severity` fires only where the consumer's severity can be read as the provider's: a single-cause consumer row that is not cascading or metastable, as §6 defines. Everywhere else the check is a reviewer rule (§11). |

**Why M4 links chains.** Classical FMEA links levels: the failure mode of a lower-level item is a cause at the next level up, and its next-level effect is that level's failure mode. The link buys three things beyond the idiom. Severity consistency: without a link, the provider's row and the consumer's row each write their own end effect and rate S on it, and across services they will disagree; with a link, a lint or a reviewer flags a provider whose S is below the S of a consumer row it feeds. Occurrence evidence: the consumer's cause is the provider's failure mode, so the provider's O and its evidence are evidence for that cause, which §11 makes a reviewer rule. And the element reference comes for free. The costs, accepted: the update-mode rules of §10, an acyclicity invariant (§5), and two chains per cross-service failure, which is the work of a multi-service FMEA rather than overhead on it.

**Why the link sits on the cause.** The consumer's analyst knows what they depend on, the cause already exists as a record, and the provider's row shows where its failure propagates by inverting the links. One relation in one place; the provider-side and two-sided variants were considered and set aside.

## 4. Data model

The schema `$id` becomes `urn:fmea-software:schema:fmea:v3`. The authored top-level parts become five: `meta`, `elements`, `functions`, `dependencies`, `chains`, written in that order, with `computed` after them as before. The keyword subset `schema.ts` interprets (`$ref` into `$defs`, `type`, `properties`, `required`, `additionalProperties: false`, `items`, `minItems`, `enum`, `const`, `pattern`, `format`, `minimum`, `maximum`, `minLength`) expresses everything below; uniqueness, cross-references, `from` differing from `to`, acyclicity and the conditional inbound-edge requirement are invariants (§5), as the existing cross-reference rules are. Every id comparison below is byte for byte, as every id comparison in the scripts is.

In `fmea.schema.json`, `$defs.dependency` and the element's `dependency` property are removed. New definitions `$defs.dependencyEdge` and `$defs.codebase` describe the edge and the codebase entry, closed by `additionalProperties: false`, with `from`, `to` and `strength` required on the edge, `dependencies` a `type: array` of edges with no `minItems`, and `sla` and `limits` of `type: string`. Their descriptions carry the F-WS3-01 citation of the old block, state the dependency from the consumer's side and not from "the analysed system", and name the invariants of §5 that govern each field: `meta.codebases[].id` names `codebase-id-unique`, `elements[].codebase` names `element-codebase-resolves`, `dependencies[].from` names `dependency-from-resolves`, `dependencies[].to` names `dependency-to-resolves` and `dependency-self`, the edge names `dependency-pair-unique`, and `causes[].chain` names `cause-chain-resolves`, `cause-chain-self` and `cause-chain-cycle`. The top-level `required` becomes `meta`, `elements`, `functions`, `dependencies`, `chains`, in that order in `properties`, and the root description says that five parts are authored, with `computed` after them. The `elementBoundary` description's last sentence becomes "An element whose boundary is not in_scope is the `to` of at least one edge in dependencies[] (invariant element-dependency-required)."

Terms. A **root** is a depth-1 element, which the report labels a top-level element; **top level** alone means the document's JSON top level. The **consumer** and the **provider** are an edge's `from` and `to` elements and, for a link, the linking chain and the linked chain. An **edge** is an entry of `dependencies[]`; a **link** is a `causes[].chain`. An **outside** element is one whose boundary is `owned_outside` or `third_party`. The **ancestors** of an element are the elements a walk reaches by following `parent` from it through the element index by id, which §5 builds once and under which a duplicate id resolves to its first element in document order; the walk stops at a parent that is `null`, that does not resolve, or whose id it has already visited, the element it started from counted as visited, so an element is not among its own ancestors. The **descendants** of an element are the elements that have it among their ancestors, and its **subtree** is the element with its descendants. Every use of these words in this design means these sets. On a document that passes the invariants they coincide with the dotted ids, because `element-parent-resolves` and `element-parent-matches-id` make every `parent` an existing element whose id is the id without its last segment. They are defined on `parent` because the lints run on a document that fails an invariant and the report's tree is built from `parent`, so one walk serves the effective codebase of §4.2, the lints of §6, the stale set of §10 and the roll-ups of §12, and the lint agrees with the tree the report draws.

### 4.1 `meta.codebases[]`

Optional; absent in a run that names no codebase, and `minItems: 1` when present, so "absent" is the one way to say none. Set in step 1, beside the boundary. One entry per codebase the run covers or reads; an outside element's repository is an entry only when the run read it.

- `id`: a plain id (`$ref plainId`), unique in the list (invariant `codebase-id-unique`).
- `name`: how the team says it (`$ref nonEmptyString`).
- `repo`: the repository in the `owner/repo` form, declared with the `pattern` `^[^\s/@:]+/[^\s/@:]+$`, the same pattern as the `owner/repo` head of the qualified repo ref in `lints.ts`, so the lint of §6 can match the two.
- `path?`: a folder inside the repository, slashes allowed, for a codebase that is part of a monorepo (`$ref nonEmptyString`).

Several entries may share a `repo`, which is the monorepo case. `path` is printed in the report header and nothing checks it, so `repo-ref-codebase` (§6) compares repositories only and does not tell apart two codebases in one repository.

No commit on the record. The qualified `repo` source ref already pins one per ref, and a record-level pin belongs to the "update one codebase alone" outcome that is set aside (§17).

`meta.boundary.included` stays as it is and describes what inside the codebases is covered; SKILL.md no longer tells the run to list codebases there (§13). A codebase whose repository the inputs do not name is not an entry: it is an open assumption, so a run never invents a repository name (§13 step 1).

### 4.2 `elements[].codebase?`

A plain id naming an entry of `meta.codebases[]` (invariant `element-codebase-resolves`). Permitted on an element of any boundary. The **effective codebase** of an element is its own `codebase` when it sets one; otherwise, when the element and its parent are both `in_scope`, its parent's effective codebase; otherwise none. Inheritance runs from an in-scope parent to an in-scope child and nowhere else, so it stops wherever the boundary changes between a parent and its child, and an element never skips its parent to read a further ancestor. A run sets `codebase` on its in-scope roots, on an outside element whose repository it read (§4.1), and on a child where it lives elsewhere, such as a shared library in its own repository, or where the child's parent is outside the boundary (§13 step 2). An element whose boundary is `owned_outside` or `third_party` never inherits: it has an effective codebase only when it sets one, so a third-party gateway nested under an in-scope root is not reported as living in that root's repository. Such an element passes nothing down either: an in-scope element nested under it inherits nothing through it, even when the outside element sets a codebase, so an in-scope adapter hosted in an `owned_outside` platform is not reported as living in the platform's repository. Where the inputs place such a child in a codebase, the run sets `codebase` on the child, and the child's own in-scope descendants inherit from it. The lint `repo-ref-codebase` (§6) and the report's codebase column and tree lines use the effective codebase; an element with none has none. The effective codebase is computed once, by one function that the lints and the report model share. It uses the first element of each id and walks the ancestors of §4 in order. A `codebase` id that names no entry of `meta.codebases[]`, or any id while the list is absent, gives the element no effective codebase, and its in-scope descendants inherit none through it; a parent that does not resolve ends the walk with none. `element-codebase-resolves` already reports the element that sets the id, so nothing more is reported for its descendants.

### 4.3 `dependencies[]`

Required at the top level; an empty array when nothing depends on anything. One entry per edge, authored in step 2 from the dependency classification of the inputs:

- `from`: the consumer, `$ref elementId` (invariant `dependency-from-resolves`).
- `to`: the provider, `$ref elementId` (invariant `dependency-to-resolves`), different from `from` (invariant `dependency-self`).
- `strength`: `strong` or `weak`, as the design-inputs checklist classifies a dependency.
- `sla?`, `limits?`: free text in the source's own terms, as before. Nothing computes on them.

A `(from, to)` pair occurs once (invariant `dependency-pair-unique`), and the pair is the edge's identity for the update mode's diff (§10). A dependency that is strong for one use and weak for another, such as writes and reads, is one edge at the stronger strength, with the split carried by the chains (§13 step 2). An edge may cross levels in either direction, so a parent may depend on its child, as checkout does on its gateway, and a child on a sibling or on an element of another root. Edges are not required to be acyclic: services call each other both ways.

An element whose boundary is `owned_outside` or `third_party` is the `to` of at least one edge; this is today's `element-dependency-required`, reworded. Such an element is an external dependency; an `in_scope` element that is the `to` of an edge is an internal dependency, as before. An outside element consumed only by another outside element is allowed, since a third-party service behind an owned-outside service is a real shape; a stricter rule is listed in §17.

### 4.4 `causes[].chain?`

Optional on every cause: a plain id naming another chain in the document, the provider's chain whose failure mode this cause is; under a duplicate chain id it names the first in document order, as every reference in the scripts does. The cause's `text` states that failure mode in the consumer's terms. The provider's chain gains no field and the link is stored only on the consumer's cause; the report derives "propagates to" by inverting the links (§12), and the reviewer rules of §11 govern what the provider's effects state on a linked pair. A linked cause may carry `origin` and `adversarial` like any other cause: the link adds no rule on them, the handoff invariants apply to the consumer's chain as they do today, and nothing compares the linked cause's fields with the provider's chain or its causes. Invariants: the id resolves (`cause-chain-resolves`), it is not the cause's own chain (`cause-chain-self`), and the link graph over the document is acyclic (`cause-chain-cycle`). A link between two chains on the same element is allowed: one mode of an element may cause another. A feedback loop between two chains is not two mutual links, which the acyclicity rule refuses, but one cascading row written to the skill's convention, with the triggering event as its cause and the amplification as its mode (§13 step 4).

### 4.5 Removed

`elements[].dependency` is removed from the schema and from `types.ts`, and `additionalProperties: false` on the element then refuses the key. Its three fields live on the edge. A v2 document that carries it is refused by the gate of §7 when it meets that gate's shape precondition, and by the schema otherwise. The element's `parent` description ends "Derivable from id; the report's tree and the ancestor walk of the lints read it." in place of "Stored for the reader; derivable from id.", since the lints now read the field.

### 4.6 Types

`types.ts` gains `Codebase { id: string; name: string; repo: string; path?: string }` and `DependencyEdge { from: string; to: string; strength: Strength; sla?: string; limits?: string }`, reusing the existing `Strength` alias, which is kept; gains `codebase?: string` on `Element` and `chain?: string` on `Cause`; gains `dependencies: DependencyEdge[]` on `FmeaDocument`, which lists `meta; elements; functions; dependencies; chains; computed?` in the authored order of §4, and `codebases?: Codebase[]` on `Meta`; and loses `Dependency` and `Element.dependency`.

## 5. Invariants

Violations are errors, reported by `validate.ts` in `errors[]`, as the existing invariants are. Nine ids are new and join `INVARIANT_RULES` in `invariants.ts` after `element-security-rationale-required`, in the order of the table below, so that they sit between `element-security-rationale-required` and `rating-review-by-date`. Their helpers run in `checkInvariants` at that point, in that order; a helper that checks several of them reports them as the existing multi-rule helpers do; and since `errors[]` is not sorted, its order follows. `element-dependency-required` already exists, keeps its place as the tenth entry, and appears in the table for its new wording and pointer only. In `quality-and-lint.md`, the nine ids join the validator-id sentence after `element-security-rationale-required`, in the order of the table below, so that the sentence keeps the order of `INVARIANT_RULES`; each also gets one row in the section "Invariants, lints and reviewer rules outside the seven lists", after the `element-security-rationale-required` row, with the rule text from the table below, without a Message clause, severity `blocker`, records `none`, enforcement `validator`, provenance `[skill-authored]`, and the existing `element-dependency-required` row gets the reworded rule from the table. Message texts the table does not give are the plan's to write, and the invariant tests pin them.

| Id | Rule | Pointer |
|---|---|---|
| `codebase-id-unique` | No two entries of `meta.codebases[]` share an id. | each later entry's `id` |
| `element-codebase-resolves` | `elements[].codebase` names an entry of `meta.codebases[]`. When `meta.codebases` is absent, every `elements[].codebase` fails it. | the element's `codebase` |
| `dependency-from-resolves` | `dependencies[].from` names an element. | the edge's `from` |
| `dependency-to-resolves` | `dependencies[].to` names an element. | the edge's `to` |
| `dependency-self` | `from` and `to` differ. | the edge's `to` |
| `dependency-pair-unique` | No two edges share `from` and `to`. Message: "edge from X to Y is listed more than once", X and Y the edge's `from` and `to`. | each later edge itself, `/dependencies/<i>` |
| `element-dependency-required` (reworded) | An element whose boundary is not `in_scope` is the `to` of at least one edge. Any edge whose `to` names the element counts, whatever its `from`, including a self-edge; `dependency-from-resolves` and `dependency-self` report that edge on their own. Message: "element X has boundary B and no edge depends on it". | the element's `boundary` (it was the element's `dependency`) |
| `cause-chain-resolves` | `causes[].chain` names a chain. | the cause's `chain` |
| `cause-chain-self` | `causes[].chain`, resolved to the first chain with that id, is not the chain, by index, that the cause belongs to; under a duplicate id a link is a self-link only when the first chain with that id is the cause's own. | the cause's `chain` |
| `cause-chain-cycle` | Over the links that resolve and are not self-links, keyed by chain index, the strongly connected components of the link graph are computed; one issue per component of two or more chains, at the link whose two ends are both in the component with the smallest (chain index, cause index). A chain that leads into a cycle but is not on it is not reported. Issues from different components are emitted in ascending (chain index, cause index) of their pointers, the document order the other invariants report in. | that cause's `chain` |

The cycle check is defined over components rather than over walks because cause links form a multigraph, two cycles can share links, and a walk-based rule would report at different pointers depending on where it started. The implementation is iterative, not recursive, so a long linear chain of links cannot exhaust the stack, and it indexes chains, functions and elements by id once, as the ancestor and descendant sets of §4 also need; the check survives dangling links and duplicate chain ids, since the invariants run together.

`dependency-pair-unique` points at the whole edge and not at one of its fields because an edge has no id and the pair is its identity (§4.3): neither `from` nor `to` is wrong on its own, and the remedy is to remove the later edge or merge it into the first at the stronger strength, which the field pointers of the id rules do not fit. Its message names both ends because the pointer names only the later edge, and the earlier edge is found by its pair. The pair is ordered: an edge and its reverse are two pairs, since services call each other both ways, and never collide.

## 6. Lints

Warnings, written to `computed.lints[]` with severity `warning`; warnings do not affect the quality score, which counts blockers only. The three new lints join `MACHINE_RULES` after `repo-ref-form`, in the order of the table below, which fixes the order of `computed.lints` that the fixture's stored block and the stale-computed check depend on. The machine lint count in `quality-and-lint.md` goes from eleven to fourteen. Every lint below skips a link, a function or an element that does not resolve, as the existing row lints do, because lints run even when an invariant fails. Each lint emits its findings in a fixed document order, stated per lint, because the validator compares `computed.lints` in order when it checks for a stale computed block. Lint messages are fixed once shipped for the same reason: a reworded message makes every stored `computed` block stale. The format change of this design is the one exception: every stored block is regenerated at v3 (§13), so the dependency-row lint's message changes here and nowhere later. Message texts the table does not give are the plan's to write, and the lint tests pin them.

A consumer row is **cascading or metastable**, for the lint below and the reviewer rules of §11, when its `trigger` restates the linked cause (trimmed text equality, as the report model matches triggers to causes) or when one of its `catalog_refs[].id` is `cat-service-01`, `cat-service-02`, `cat-service-03`, `cat-service-05`, `cat-dependency-03` or `cat-dependency-04`; on such a row the severity is the consumer's own amplification and says nothing about the provider. The six are the catalog's positive-feedback rows: cascading failure, metastable failure, retry amplification, recovery storm, cold or contagious failover and reconnection stampede. Each puts the loop in the mode or the cause, and five of them put a distinct initiating event in `trigger`, so on a row written to the catalog's convention the id arm exempts it whether or not the trigger arm also does. `cat-service-04`, `cat-service-06`, `cat-dependency-01` and `cat-dependency-02` are left out: on those rows the consumer's effect is the provider's failure carried through, which is the pair the lint exists for. The six ids are one constant in `lints.ts`, compared whole and never by prefix or range, since `cat-dependency-01` shares the prefix and `cat-service-04` sits inside the range. A catalog row added later whose mode is a positive-feedback loop joins the list by a change to the lint, which makes stale any stored computed block whose findings it changes, as any change to a lint does. The trigger arm also takes in an ordinary single-cause row whose trigger restates its cause, as the Occurrence lint and the catalog's trigger convention invite; that loss is accepted, because such a row still falls to the reviewer check of §11, and dropping the arm would flag every cascading row written to the convention without a catalog ref.

| Id | Rule |
|---|---|
| `repo-ref-codebase` | While `meta.codebases[]` is present: a qualified `repo` source ref whose `owner/repo` head is the `repo` of no entry is flagged; otherwise a qualified `repo` ref on an element that has an effective codebase, whose `repo` is a different repository, is flagged. The `owner/repo` head is the ref's text before its first `@`, captured by a new group in `QUALIFIED_REPO_REF` and carried on each repo ref beside the commit. It is compared byte for byte, case included, as ids are, with each entry's `repo` (so `Acme/Checkout` and `acme/checkout` are different repositories), and in the second check with the effective codebase's `repo`. One finding per ref, the first check winning, by element index then source index, at the ref's `ref` field, `/elements/<i>/sources/<j>/ref`, as `repo-ref-form` points. Unqualified refs are not checked; an element with no effective codebase, including one whose own or inherited `codebase` names no entry, gets only the first check, and a child does not fall back to a further ancestor; nothing is flagged while the list is absent. |
| `cause-chain-unlinked` | Let C be the element of the cause's chain and P the element of the linked chain, each reached through its function. Not flagged when P equals C, when P is a descendant of C, or when some edge runs from an element in {C, its ancestors, its descendants} to an element in {P, its ancestors}; ancestors and descendants are the sets of §4. Otherwise flagged at the cause's `chain`, by chain index then cause index: the link crosses neither downward containment nor a recorded dependency. A warning and not an error, because a team may arrange its hierarchy another way. |

Severity flows from the top of the net, so a provider whose failure is the whole cause of a worse consumer effect is under-rated. Read from `ratings` only, never from `post_ratings`. | `dependency-row-without-dependency` (reworded) | A chain whose function resolves to an element that is the `to` of no edge cites a `cat-dependency-` catalog ref. Same id, same severity, same order and same pointer as today; its message tail changes from "which carries no dependency block" to "which is the provider of no edge". |

## 7. The legacy gate

A second pre-schema check runs after the v1 check in `legacy.ts`, so a v1 document still gets its `KIND_LEGACY` message first. Both checks share the v1 gate's shape precondition: an object whose `elements` is an array of objects; anything else is left to the schema stage, as today, so a non-analysis still gets schema lines and the existing test for that input holds.

A document is a v2 document when its top level has no `dependencies` key (pointer `/dependencies`), or when any element carries a `dependency` key (pointer `/elements/<i>/dependency`). The gate reports one issue, the first trait in that order (the top level, then elements in document order), with code `DEPENDENCY_LEGACY`, rule `format-legacy`, and a message of the shape `document predates schema v3 (<reason>); <both remedies>`, the reason being `no top-level dependencies array` for the top-level trait and `element <id> has a dependency block` for the element trait, and the remedies that a new analysis adds the top-level `dependencies` array, empty when nothing depends on anything, and that an analysis written against 0.3.x to 0.5.x is migrated through the "Migrate a v2 document" section of SKILL.md; the version range follows the version of §14 if that is renumbered. `DEPENDENCY_LEGACY` joins `CODES` with the validation exit status, and `validate.ts`, `render.ts` and `track.ts` refuse the same way because all three call `validateDocument`. The `format-legacy` row of `quality-and-lint.md` gains the two v2 traits beside the v1 ones.

A v3 document that merely omits the key is told to add it, so the schema's `required` entry for `dependencies` is reached only when the shape guard does not apply. A document that has `dependencies` and also an element with a `dependency` key is told to migrate, and the migration merges the blocks into the existing array, under §8's rule for a pair already present.

## 8. Migrating a v2 document

Performed by the skill's update mode, recorded in `meta.history`, bumping `meta.version`, and run alone, never in the same update as an architecture change, as the v1 migration is. When it writes the migrated JSON it ends, as every run does, with step 7's sequence, `priority.ts --write`, `validate.ts --write`, then `render.ts`; when it writes nothing, it runs none of them. The rules go in `structure-elements.md` under a heading beside the v1 ones.

- `dependencies[]` is created when absent and kept when present. Each element's `dependency` block becomes an edge whose `to` is the element and whose `strength`, `sla` and `limits` are the block's, one edge unless a rule below makes several or none; the block is removed. A document with no block and no array gets an empty array.
- An edge the migration would make, by any rule below or by a consumer the person names, whose `(from, to)` is already an edge of the existing array is not added: the existing edge is kept as it is and the block's values are dropped for that pair. When the block's strength, SLA or limits differ from the kept edge's, the difference is listed in `meta.assumptions[]` as an open assumption owned by `user` that carries the block's values. Under M8 this moves no rating.
- The edge's `from` is the element's nearest `in_scope` ancestor. Strength moves no rating (M8), so no rating depends on where strength is written or which in-scope ancestor the edge comes from; the migration marks no row stale. A migrated rating may rest on the removed exclusion: under v2 a chain whose function belongs to an element whose `dependency` block was `weak` was rated from the wrong-result class even where the run found loss of access credible, a finding v2 asked the run to record as an open assumption, so its S can sit a band below what v3 reads from the same end effect, and the document carries no mark that says which chains those are. The migration re-rates nothing and marks no row stale for it, since no stale rule of §10 fires on a block that became an edge of the same strength and the scales version does not move (§11). Instead it writes one open assumption owned by `user` that names, by chain id, every chain whose function belongs to an element whose block was `weak`, whether or not the block became an edge, and says that each was rated under an exclusion v3 removes and is to be re-read against its failure mode and its end effect as written; a v2 assumption that recorded the classification doubt stays beside it. The set is computed from the document, the same attended and unattended, and no assumption is written when no block was `weak`. The person settles each named chain afterwards. Where loss of access is not credible, nothing moves. Where it is, the classification and the effect disagree, the case §11 names, and the person decides which stands. Where the consumer does not complete without the provider, the classification was wrong: the person sets the edge's `strength` to `strong`, or adds the consumer's edge, in an ordinary update, an edge change that marks the provider's rows stale under §10 and re-reads S from the rewritten end effect. Where the classification stands and it is the provider's own function whose outcome is lost, the edge stays `weak`, the open assumption on its strength that §11 requires is recorded, and the row is re-read when a later update marks it stale; until then its rating stands as written and that assumption carries the doubt, as §10 does for any finding on a row outside the stale set. No other route re-rates a named chain. A chain is settled when nothing moves, when an edge change has re-read it, or when the §11 assumption on its strength carries it; the assumption closes when every chain it names is settled, and an update that settles some of them rewrites it to name the rest.
- For a provider with no in-scope ancestor, `from` is the one other in-scope root when exactly one exists. When several exist the person is asked, and may name one or more consumers, each of which gets an edge; unattended, the first such root in document order is taken and listed in `meta.assumptions[]` as an open assumption owned by `user` that names the other in-scope roots as candidates.
- When no other in-scope root exists: an `in_scope` provider has its block dropped, gets no edge, and the drop is listed as an open assumption owned by `user` that carries the block's strength, SLA and limits, since it validates without an edge; an outside provider cannot validate without one, so the person is asked to name a consumer, which may be a nested in-scope element, and unattended, since this is the one migration question with no default, the whole update stops: the file is left as it was, with no edge, no history entry and no version bump, and that includes the v1 half of a combined v1-then-v2 update; the final message names each outside provider that has no consumer and asks for one. A question of this migration with a stated default, the first in-scope root among several, takes it unattended as an open assumption owned by `user`.
- A v1 document runs the v1 migration and then this one in the same update, with every v1 boundary decision, whether the person answers it or it is defaulted, settled before any `from` is chosen, because the `from` rules read the migrated boundaries: one version bump, one history entry naming both. The v1 rule that keeps the `dependency` block becomes "its `dependency` block is carried into the v2 migration's edge".
- The migration adds no codebase and no link. Both are later work for the person, through an ordinary update, and the migration's final message says so, and says that until links exist an edge change marks only the provider's rows stale, so a migrated document has less stale coverage than one authored against v3. The final message also names the chains the weak-block assumption lists, or says that no block was `weak`.
- The history entry names the edges made, each with its `from` and the rule that chose it, each existing edge kept in place of a derived one, and the chains the weak-block assumption lists.

A role or boundary the person changes afterwards, an edge they add or change, and a link they add, all go through the ordinary update rules of §10.

## 9. Converting a sheet

The declared default for an item that gets an edge and has no strength in the sheet stays `strong`, whatever its boundary: an outside item, and an in-scope item whose rows carry an SLA or limits but no strength; the edge's `strength` takes it, as `dependency.strength` did in v2, and the fail-safe rationale stands. Every outside item, whether or not the sheet carries a strength, gets one edge whose `from` is the first in-scope item in sheet order; an in-scope item whose rows carry a strength, an SLA or limits is an internal dependency and gets the same edge, from the first in-scope item other than itself, and when no other in-scope item exists its values go into an open assumption and it gets no edge. Rows of one item that disagree take the stronger strength, as §4.3 does for a dependency split by use, and the first row's SLA and limits, the other rows' values going into the edge's open assumption. Each edge gets its own open assumption owned by `user`, naming the edge's `from` and `to`, the rule that chose the `from` (the first in-scope item in sheet order, the first other than itself for an in-scope item, or the person's naming), and the strength and whether it came from the sheet or is the `strong` default; the column mapping in `meta.history` records the edges as a declared substitution, counted like the others, and drops any wording about a `dependency` block. Neither the strength default nor the consumer comes from the sheet; both are recorded, and under M8 neither moves a rating or a row. A sheet with no in-scope item has no item to default a consumer to, so the conversion stops and asks the person to name, for each outside item, the item or items that consume it; any item may be named, an outside one included (§4.3), and each named consumer gets an edge recorded as in the column mapping. Unattended, the conversion writes nothing and ends with that question in its final message, as the migration does (§8). The conversion adds no link, even where a Cause cell restates another row's Failure Mode, and the linking pass of §13 step 4 does not run on a converted sheet; it adds no codebase; both are later work for the person through an ordinary update, as §8 says of migration, and the final message says so. In the legacy fixture the edge is from the checkout interface to the gateway, a declared default a practitioner will want to correct, which the assumption invites.

## 10. Update mode

Replaces the sentence of SKILL.md and of `structure-elements.md` that lists the fields that make an element changed, as §13 lists; the main design's §5 receives the dated amendment note of §14.

- **Edges are diffed by `(from, to)`.** An edge is added, removed, or changed in `strength`, `sla` or `limits`. An edge field the new inputs do not restate is carried forward and is not a change. An edge whose consumer element was removed or re-parented is a removed edge; when the inputs still state the dependency, the update writes it again under the consumer's new id, and that is an added edge by identity. Both the removal and the addition mark the `to` element changed, so moving a consumer marks the provider's chains stale even when strength, SLA and limits are unchanged; that cost is accepted. An edge whose provider element was removed goes with the element, and the removed element's chains go with it, so nothing is left to mark; a re-parented provider is a removed element and a new one, its old edges go with it, and an edge written again to its new id is an added edge whose `to` is a new element with no rows to mark.
- **An outside element left with no consumer.** After the edge diff, counting an edge written again under a re-parented consumer's new id, an element whose boundary is not `in_scope` and that is the `to` of no edge fails `element-dependency-required`, whether its last edge went with a removed or re-parented consumer, was removed on its own, or the inputs add the element with no consumer; the condition is the invariant itself, read off the draft. The update does not decide for the person. Before any row is marked stale, since the answer decides the stale set, it asks one question per such element, naming the element, what left it without a consumer, the descendants, functions and chains that would go with it, and each action on those chains that carries a `tracker` block. The answer is one of two. Either the person names one or more consumers, each any element the update keeps other than the element itself, a nested in-scope element or another outside element included (§4.3), each with the strength, SLA and limits the person gives; each named consumer's edge enters the diff by its `(from, to)` pair like an edge the inputs state, so a pair the document already had with no new values changes nothing, and a new pair is an added edge that marks the element's chains stale under the rules below, its strength, when the person gives none, taking `strong` as an open assumption owned by `user`. Or the person confirms the removal, and the update removes the element as a removed element, with its descendants, whose `parent` cannot resolve without it, their functions and chains, and every edge at either end of them; for an element the inputs add, the removal means it is not added. A descendant the person keeps is re-parented in the new structure and is a removed element and a new one; each link into a removed chain is handled by the removed-chain rule below; and a removed edge whose `to` remains marks that element changed under the next bullet. The check then runs again on the result, because a removed element may have been the last consumer of another outside element, and each such element gets its own question in the same update. The update removes nothing without that confirmation. The update summary in `meta.history` lists each element, function, chain and edge removed, each link dropped or repointed, and the tracker link of each removed action that carried one, since the item stays open in the tracker until the person closes it; the update changes nothing in the tracker. Unattended, the question has no default, so the update writes nothing and ends with the question in its final message, as §8 and §9 do: the file is left as it was, with no history entry and no version bump, and the message names each such element and what left it without a consumer, and asks for a consumer or for leave to remove it.
- **An element changed** when its `kind`, `boundary` or `security_relevant` changed, or when an edge whose `to` is the element was added, removed or changed. A strength change counts although strength moves no rating, because strength selects the provider's next-level and end readings and the open-assumption check of §11, so the row is re-read. Name, description, sources, security rationale and codebase are labels and do not count. A change of `parent` is a change of `id`, a removed element and a new one, as before.
- **The rows an edge change marks stale** are the chains on the `to` element, and the chains that link through a cause into a chain on the `to` element and whose own element is `from`, an ancestor of `from` or a descendant of `from`: the consumer side of the set whose links the lint of §6 accepts across that edge, and on the provider side only the exact `to` element, as a dependency-block change was in v2. A link into a chain on a descendant of the `to` element is not reached, and that asymmetry is accepted. The reason is `element-changed` for both (M7), a newly flagged row takes `since_version` under the existing rule, and the ordering rule among reasons is unchanged. On a consumer-side row the stale notice's fixed words, "its element changed", name an element that did not itself change; M7 accepts that imprecision, and §17 lists `dependency-changed` as the alternative. What such a row re-reads is the carry-forward rule below, which is the same on both sides of the edge.
- **A removed chain breaks every link into it.** The update repoints each `causes[].chain` that named it only to the chain the same update writes in the removed chain's place, such as the chain's new id after a re-parent, and never where the repointed link would be a self-link or make a cycle; otherwise it drops the link. Unattended, the update follows this rule without asking. The update summary in `meta.history` lists each link dropped or repointed. A dropped link marks no row stale; the cause text stays.
- **A removed codebase** still named by an element has that element's `codebase` repointed by the update when the inputs place the element in another listed codebase, and otherwise cleared; each is listed in the summary; a cleared in-scope root is an open assumption owned by `user`, and its in-scope descendants then inherit nothing (§4.2); when the last codebase goes, `meta.codebases` is dropped rather than left empty. A changed codebase, the same id with a new `name`, `repo` or `path`, marks nothing stale; where `repo` changed, the update rewrites the `owner/repo` head of each qualified source ref that names the old repository, and lists them in the summary; an added codebase is listed in the summary too, and no codebase change marks a row stale.
- **An added or changed link marks nothing stale.** A re-rated provider marks no consumer stale either. The lint of §6 and the reviewer rules of §11 catch a disagreement after the fact, and the update summary lists every consumer cause whose linked chain had its failure mode rewritten or its O re-rated in that update, so the consumer's analyst sees it.
- **A finding on a row outside the stale set is never acted on by re-rating.** The stale set is every row whose `stale.flag` is true once this update's marking is done, including rows still flagged from an earlier update. For a finding on any other row, such as a disagreement the lint of §6 or the reviewer rules of §11 raise, the update lists the finding in the update summary in `meta.history` and names it in the hand-over message. It leaves that row's ratings and `stale` unchanged, and it may record the finding as an open assumption in `meta.assumptions[]` owned by `user`. A person's re-score of the row, or a later update that marks it stale, acts on it. The update rewrites ratings on stale rows only, as before.
- **The carry-forward rule** in `scales-software.md` changes one phrase: `element-changed` re-reads S from the end effect as the update rewrites it on the stale row, and O from that end effect and, where an edge changed, the SLA and limits, as they now stand, of the edge whose addition, removal or change marked the row stale; every other factor carries forward. The rule is the same on the provider's rows and on the consumer-side rows an edge change marks stale: steps 4 to 6 re-run on every stale row, and the edge's SLA and limits enter the re-read only where the existing anchors read them, as a budget the end effect is stated against and as a stated limit that sets the vulnerable state. No rule reads the provider's O value into the consumer's O. The consumer row's O rationale for the linked cause cites the provider's O and its evidence under the reviewer rule of §11, at a re-rating as at a first rating; where a stale row links into a chain whose own row is stale in the same update, the provider's row is re-rated before the consumer's, an order that exists because links are acyclic (§5). A provider re-rated when its consumer is not stale reaches the consumer's analyst through the update summary, as the bullet on links above says. A change of strength alone changes no fact the anchors read, only the catalog's default readings, so the re-read returns the prior values unless step 4 rewrites an effect; that cost is accepted.
