# The scripts

The skill runs five scripts in `skills/fmea-software/scripts/`. They are TypeScript that Node 24.2 or later runs directly. `validate.ts`, `priority.ts`, `render.ts` and `update-check.ts` have no dependencies; `track.ts` needs `gh` for a GitHub target and `acli` for Jira. Nothing else reaches the network.

Every script refuses a document in which one object carries the same key twice, with `IO_READ` naming the key and its object; a JSON reader keeps only the last value, and the next write would remove the first. A failure prints one line, `error <CODE>: <message>`, with ` at <pointer>` when located. Exit 1 is a usage failure, 2 a validation or update-check failure, and 3 an I/O failure.

| Script | Flags and what it does | Refusals |
|---|---|---|
| `validate.ts <analysis.json>` | `--write`, `--table-file`. Runs the schema checks, invariants, priority recomputation and machine lints, and computes the quality score. `--write` replaces `computed` on a clean run. | Writes nothing on a finding; exits 2. |
| `priority.ts <analysis.json> --write` | `--table-file`, `--change-table`. Writes each row's `priority` from its `ratings` and `post_priority` from `post_ratings`, and records the loaded table's id in a document holding none. | `TABLE_ID_MISMATCH` for another table; `USAGE` for `--change-table` with no recorded table or the loaded one. |
| `render.ts <analysis.json> --out <report.html>` | `--force`, `--table-file`. Runs `validate.ts`'s checks and renders one self-contained HTML file; `--force` overwrites. Prints one line counting provisional ratings against all ratings. | Everything `validate.ts` refuses, and `COMPUTED_MISSING`, `COMPUTED_STALE`, `IO_EXISTS`, `VOCABULARY_READ`. |
| `track.ts plan\|apply\|refresh <analysis.json>` | `--table-file`. `plan` writes nothing and prints the plan with its digest. `apply --plan <digest>` takes `--only <key>,<key>` and `--public-ok`, and writes each link into the action. `refresh [--write]` reads each linked item and proposes; never changes a status. | `TRACKER_PLAN` for a stale digest, `TRACKER_PUBLIC` for a public or unknown-visibility target without `--public-ok`, `TRACKER_CONFIG`, `TRACKER_UNAVAILABLE`, `TRACKER_REJECTED`. |
| `update-check.ts <stored copy> <draft>` | `--check`. Writes nothing. Prints the structural diff, the stale set with each row's rule, links into removed chains, removed flows, outside elements with no consumer, and the re-rate order. `--check` compares the draft with what it prints. | `UPDATE_BASELINE` for a copy that is not the draft's baseline; `UPDATE_MISMATCH` for a draft whose flags, ratings or links disagree, a chain naming a removed flow, or a chain naming a flow with no non-catalog source. Both exit 2. |

`validate.ts --write`, `priority.ts --write`, `track.ts apply` and `track.ts refresh --write` read the file again just before replacing it. If another program saved it after the script read it or last wrote it, the script refuses with `IO_CHANGED`, leaves the file as saved, and exits 3; run the command again, or `plan` again after `apply`. Do not edit the file while such a command runs.

The shipped priority table is `skills/fmea-software/data/priority-fmea-software-v1.json`, the skill's own. `priority.ts`, `validate.ts`, `render.ts` and `track.ts` take `--table-file` for another table, read from no other location, and a shape-valid table is refused only when an id, an ordered vocabulary, tiling bands per factor or a cell for every band combination is missing. A table that breaks a priority property is used all the same: `priority.ts` prints one `warning priority-table-property:` line per broken property, naming its cells, and `validate.ts` records the same warning. Once a document records a table id, a run loading another is refused with `TABLE_ID_MISMATCH`; only `priority.ts --write --change-table` changes the record, on the person's request.

## Compatibility between versions

Version 0.3.0 moved the analysis to schema v2: every element carries a boundary and a security flag, replacing the `external_dependency` and `security_component` kinds. `validate.ts`, `render.ts` and `track.ts` refuse a document written against 0.2.x or earlier with `KIND_LEGACY`; the skill's update mode migrates it.

Version 0.6.0 moved the analysis to schema v3: dependencies are edges in a top-level list, from consumer to provider, and a cause may link to another chain. A document written against 0.3.x to 0.5.x is refused with `DEPENDENCY_LEGACY`. A document from 0.2.x or earlier is refused with `KIND_LEGACY`, and both migrations run in one update. An earlier plugin refuses a v3 document with schema lines, because its schema rejects the new part.

Version 0.7.0 added the flow model and kept schema v3, whose `$id` is unchanged. A document may carry a top-level `flows` array and a `flows` array on each chain; both are optional, so a 0.6.0 document still validates. The compatibility runs one way: a 0.6.0 plugin refuses a document carrying flows, with one `SCHEMA` line per flow array, and refuses a row stale with reason `flow-changed`. The flow model also moved the scales to version 2, so the next update marks every rated row stale with reason `scales-version` and advances the pin.

The validator of 0.1.0 refuses a tracker target or link, and those of 0.2.0 and 0.3.0 also refuse a Jira target, so people sharing a document must share the plugin version too. A document validated by an earlier version can carry `computed` results the current `validate.ts` computes differently; run `validate.ts --write` before `render.ts`.
